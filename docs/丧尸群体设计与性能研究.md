# 丧尸群体设计与性能研究

归档日期：2026-11-03。范围：本会话的模型选择、Blender测试结论、500只同屏讨论与后续验证顺序。

## 状态与使用方式

后续已获工程师确认并实现独立动态实验，新增结果见[群体测试模块](../src/丧尸群体测试/README.md)和[动态容量报告](../reports/丧尸模型/五百只同屏性能测试报告.html)。下文保留最初讨论时的预算与准备依据，不能覆盖新增实测的环境、版本及待测范围。

**这是研究归档，不是已批准的游戏功能或性能验收。** 工程师已要求归档本会话经验与相关模型。正式游戏主题仍待确定；500只是讨论中的同屏规模，不能替代现有载具原型范围，也不表示已承诺500只稳定60 FPS。

模型入口见[资料归档说明](../research/丧尸模型/资料归档说明.md)，实测依据见[模型测试报告](../reports/丧尸模型/模型测试报告.md)。原件、当前测试工程、历史工程和待生成运行包分别管理。

## 一、当前模型能证明什么

| 内容 | 已有证据 | 结论边界 |
| --- | --- | --- |
| 13只角色 | 每只796或800三角形，合计10392 | 面数适合作为俯视群体候选，不等于整包可直接复制使用 |
| 单只拆分 | 编号0由共享287骨骼中提取23骨，721次变形顶点比较通过 | 其余12只未逐个完成拆分动画验收 |
| 动画 | 单段约29.98秒，原地踉跄、弯腰、抬头和转向 | 整段首尾不匹配；移动、攻击、受击、死亡仍需整理或验证 |
| 材质变化 | 整体乘色试验通过 | 皮肤和衣服同时变化，分区换色需遮罩或调色板整理 |
| 群体表现 | 100只不同姿态与朝向的静态预览 | 仅用于判断风格、密度与重复感，不是动态性能证据 |

选模时优先检查轮廓、有效绑定、动作组织和材质数量。低面数、文件可下载、有动画标签都不能单独证明适合实时群体。

## 二、500只同屏的粗略预算

以下为根据当前模型推算的数量，不是硬件测量：

| 项目 | 推算 | 注意事项 |
| --- | --- | --- |
| 三角形 | 500×约800，约40万 | 不含场景、载具、尸体、特效及额外渲染过程 |
| 骨骼 | 假设每只23骨，共约11500骨 | 23骨仅已有一个完整拆分实例；总数不能直接换算FPS |
| 基础绘制 | 普通单网格、单材质独立角色约500次 | 阴影等过程额外计算；共享材质不会自动合批 |
| 全互相比较 | 500×499÷2，共124750对 | 这是每轮无序配对数，实际耗时还取决于检测内容和频率 |

优先分别测CPU动画插值与矩阵、绘制提交、GPU蒙皮与像素处理、群体逻辑。常规骨骼蒙皮的顶点变形通常已经在GPU执行；所谓GPU动画烘焙，主要进一步减少CPU逐只求动画姿态的工作，不能表述为原来所有顶点都在CPU变形。

## 三、建议的优化顺序

### 1. 先整理资产并建立普通骨骼基线

- 先选2至3种主轮廓，逐只拆分、核对蒙皮与实际动作；用颜色、尺度、朝向和播放起点增加变化。
- 同类角色共享几何、贴图和动作数据，避免重复加载整包及不必要的数据副本。
- 保留每只约800三角形作为第一轮基线，不先以进一步减面替代动画和逻辑测量。
- 整理方向稳定、脚底接触合理的待机、移动、攻击、受击、死亡片段；检查循环、状态切换与根运动。

### 2. 群体逻辑采用共享方向与局部避让

- 追逐同一目标时，优先试验共享流场或路径缓存；目标和障碍变化时更新。
- 地面二维空间网格查询附近邻居；局部拥挤时限制每次处理量，并验证不能穿墙或永久卡住。
- 身体采用圆形或胶囊近似，避免逐三角形检测；攻击、命中和视觉表现的更新频率分别管理。
- 感知、重新选目标和重新寻路分批执行，避免全部角色在同一帧触发。

可从感知与重寻路5至10 Hz、移动与避让20至30 Hz、显示60 Hz插值开始试验。这些是待调起点，不是已确认规则。使用时间戳和固定步长维护逻辑时间，不能靠累计休眠；命中可靠性不得随视觉降级而失效。

### 3. 按瓶颈决定是否引入烘焙动画与实例化

普通骨骼方案先提供可测基线。如果CPU动画更新或绘制提交超出预算，再考虑离线烘焙骨骼矩阵或顶点动画，由实例保存动作、播放时间、速度、位置与朝向。

烘焙重复动作适合大量群体，但动作混合、临时关节控制、包围体、拾取和阴影都要专门适配。减少Mixer数量本身也不能保证骨骼更新和绘制开销消失。

`InstancedMesh`面向相同几何与材质的多个实例，可减少Draw Call并设置实例颜色；它不是把任意GLB变成独立动画群体的一步转换。13种不同网格通常仍需分别组织批次，合并贴图不会自动合并所有绘制。[官方文档](https://threejs.org/docs/pages/InstancedMesh.html)

`AnimationObjectGroup`共享动画状态且要求属性兼容；它本身不是绘制合批工具。[官方文档](https://threejs.org/docs/pages/AnimationObjectGroup.html)

Three.js官方WebGPU骨骼实例化示例共享一个Mixer与动画状态，可用于理解批量蒙皮；不能直接作为500只独立动作、攻击和死亡均已解决的证明。是否采用WebGPU需另行评估，不因500只目标直接切换渲染路线。[示例源码](https://github.com/mrdoob/three.js/blob/dev/examples/webgpu_skinning_instancing.html)

### 4. 控制阴影、像素和对象生命周期

- 试验批量脚底阴影，限制投影灯与真实动态阴影覆盖；阴影贴图会增加绘制过程。[官方阴影说明](https://threejs.org/manual/pages/shadows.html)
- 简化灯光与远景法线细节，控制血雾、烟雾等透明重叠；三维内部渲染分辨率与清晰UI分别管理。
- 尸体死亡动作结束后转静态，设留存上限；角色、血迹和伤害数字复用对象，观察回收暂停和内存增长。
- 角色全部同屏时，视锥剔除不能直接减少这500只的数量。动画和模型分级还应考虑屏幕像素大小、缩放与交战重要性；正交镜头不能只按与相机距离推断可见尺寸。

大量对象的场景节点和绘制请求本身有成本；共享资源与合批分别测量。[官方优化说明](https://threejs.org/manual/pages/optimize-lots-of-objects.html)

## 四、后续验证顺序与记录要求

建议在同一设备、浏览器、镜头和分辨率下，先按100、300、500只递增，再逐项开启：

1. 静态角色，确认几何、材质和绘制提交基线。
2. 动画，测CPU姿态更新、矩阵和GPU蒙皮。
3. 移动、寻路、局部避让，测逻辑及高密度退化。
4. 攻击、命中、死亡、对象回收，测集中事件峰值。
5. 加入实际地图、载具、阴影、爆炸与声音，检查完整场景。

记录CPU与GPU型号、浏览器与实际渲染GPU、显示和内部渲染分辨率、画质、角色数、活动骨数、Draw Call、三角形数、帧时间中位数与P95、峰值、内存趋势和测试时长。CPU与GPU可重叠工作，不把其耗时直接相加为整帧时间。

60 FPS对应约16.7毫秒一帧，30 FPS约33.3毫秒。观察稳定性及最差场景：500只密集靠近、同时攻击、集中死亡、镜头缩放和大面积特效。只显示平均FPS不足以验收。绘制统计可参考`renderer.info`，它不代替CPU/GPU耗时分析。[官方文档](https://threejs.org/docs/pages/WebGLRenderer.html)

**当前未实施上述动态群体测试，没有500只FPS、GPU耗时或承载上限结论。** 后续开发仍应提交具体实施计划，获得确认后执行。
